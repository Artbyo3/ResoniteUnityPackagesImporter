# Offline bug audit — 2026-10-08

Local review-branch follow-up, based on the movement-parent checkpoint. This is
inspection and diagnostic work only: no production code, installed mod, live
world, public documentation site or GitHub state was changed by this audit.

## 1. Missing textures cannot recover through the companion-package flow (P2)

**Trigger:** a package includes its material files, but a referenced texture is
in a second package. A related case is supplying a missing material first and
its textures later.

**Evidence:** `FileImportHelperTaskMaterial.ImportTextureCore` (lines 255–258)
logs an absent texture GUID and returns null. Unlike missing material files,
this does not register a dependency. `UnityProjectImporter` tracks only
`MissingMaterialBinding` entries; `CanResolveAnyMaterial` (lines 93–99) matches
only their material GUIDs. Consequently, a texture-only omission does not open
the companion prompt, and a texture-only package cannot satisfy that lookup.
Material restoration marks the material binding resolved even if conversion
returned a material with missing texture targets.

There is a second obstacle to repairing the same import: `ImportTexture`
(lines 244–248) caches the null result in `AsyncImportCache`. That cache has no
invalidation. Supplying assets later does not cause that texture key to reload;
converted materials are also cached independently.

**Offline reproduction:** compiled the actual production `AsyncImportCache`
source with a loader that returns null for an absent asset. Added the asset,
then requested the same key again: result remained null and the loader ran
only once. This proves the cache behavior; the texture registration and UI
consequences above are source-traced, not exercised in Resonite.

**Future fix direction:** model texture dependencies alongside material
dependencies, retaining enough information to update the affected material
fields. Define cache invalidation/retry when the dependency index changes.
Keep successful shared imports deduplicated. Merely showing the popup for
textures will not resolve the cached conversion or missing assignments.

**Acceptance fixture:** material present / texture absent, then drop a
texture-only companion package; also test material-first then texture-later.
The station preview should update and only report ready once the required
dependencies are resolved.

## 2. Outfit revision checks miss changed dependencies (P2)

**Trigger:** reinstall an outfit whose prefab GUID and YAML are unchanged but
whose referenced material, texture, mesh, or nested prefab has changed.

**Evidence:** `OutfitInstallIdentity.FromPrefab` (lines 26–38) hashes only the
prefab file. `ModularAvatarAttachmentInstaller.InstallCopyAsync` (lines 373–381)
returns the existing installation for an identical hash. The new dependencies
are neither detected as an update nor applied. This also matters when an old
installation has placeholder materials and a later import resolves them without
changing the prefab YAML.

**Offline reproduction:** called the actual production identity helper on a
prefab referencing a material; changed the material while keeping the prefab
unchanged and computed the identity again. `Compare` returned `Current`.
The installer early return is verified in source; no live outfit was modified.

**Future fix direction:** distinguish stable prefab identity from the effective
installation revision, including relevant dependency content and conversion
inputs. A changed revision should at least be reported as such; this does not
authorize automatically replacing an installed outfit. Plan existing-record
compatibility when changing the fingerprint/schema.

**Acceptance fixture:** unchanged prefab with a material-only or mesh-only
update must not report the old installation as current. Identical complete
imports should remain idempotent.

## 3. Two stations can race to install the same outfit (P2)

**Trigger:** two stations install the same outfit onto the same avatar before
either finishes. Use a simple outfit whose mapped bones already exist, so no
additional retained-bone conflict prevents the second installation.

**Evidence:** station `busy` is an instance field, not an avatar-wide guard.
Each `InstallCopyAsync` checks for an installation record once at line 373 and
duplicates the outfit at line 396. It then awaits bounds stabilization at
line 547 (three engine updates) before creating the record at line 557. There
is no shared reservation or second identity check before that commit.

Possible ordering: A finds no record and yields; B finds no record and yields;
A creates its record; B creates another. A single engine update thread does
not prevent this async interleaving. Both copies and optional menu controls can
remain on the avatar.

**Verification level:** concrete source-level race, not reproduced in-world.
The current offline suite does not execute the engine-dependent installer.

**Future fix direction:** serialize or reserve installation by world, target
avatar and outfit identity before lookup/duplication, with cancellation-safe
release. Recheck target validity and existing records under that reservation;
do not globally block unrelated avatars or leave a failed reservation behind.

**Acceptance fixture:** trigger the same install from two stations together.
Exactly one installation and one control set should result. Repeat with the
first operation cancelled or failed while the second is waiting.

## Additional user observation: inconsistent materials between prefab variants

The user reports that some avatar and clothing packages contain several prefab
variants, but sometimes only one receives the expected material appearance;
other variants have gray materials. Recorded after the audit as a reported
symptom, not a reproduced or diagnosed defect. No specific fixture or failing
renderer has been captured for this report yet.

Do not equate gray output with a shader-conversion failure or assume this is
the missing-texture issue above. The variants may reference different assets,
carry different overrides, or receive different renderer assignments. Whether
this occurs before or after a companion package is supplied is also unverified.

For the next diagnostic pass, compare a correct and a gray variant from the
same package: renderer identity, serialized material GUIDs and prefab overrides,
resolved material/texture providers, fallback assignments, and missing-material
registrations. Check that copied renderers receive the intended per-variant
bindings when sharing imported assets. Recheck every variant after companion
resolution and after switching away and back. Use a fresh import to distinguish
source data from stale preview or installed-output state.

Success means each variant displays its own authored materials when all required
assets are available; unresolved references are reported for the affected
variant instead of being silently treated as a successful conversion. Preserve
the three audit findings above as separate follow-ups until evidence connects
them to this symptom. No production change was made for this report.
